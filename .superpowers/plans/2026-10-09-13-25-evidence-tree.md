# Evidence Tree Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Link each business rule to the playbooks that validate it and to the history of their executions, readable through three MCP tools and `cli.py evidence`.

**Architecture:** Rules and playbooks are Markdown notes with YAML front matter in the vault, read by `core/evidence.py`. Executions are rows in a local SQLite file written through `core/evidence_store.py`. `brain_mcp` exposes the tools; each recorded execution carries the `trace_id` of the MCP call (step 0). Nothing here runs a test.

**Tech Stack:** Python 3 (`.venv`), `sqlite3`, `PyYAML` (`yaml.safe_load`), `fastmcp==4.0.11`, `click`, `unittest`.

**Spec:** `.superpowers/specs/2026-10-09-13-12-evidence-tree-design.md` (the branch `feat/evidence-tree` is stacked on `feat/mcp-trace-ids`, PR #1: it uses `core.tracing.current_call`).

## Global Constraints

- Ids: `RULE-NNN` and `PB-NNN`, three digits, unique across the vault. Results: `pass`, `fail`, `error`, `skipped`. Environments: `hml`, `production`, `local`. Statuses: `draft`, `active`, `retired`. Sources: `reported`, `imported`.
- Definition notes live in `vault/rules/` and `vault/playbooks/`. Each note starts with a `---` fenced YAML front matter block, followed by a first-level heading (the dashboard takes the title from the first `# ` line) and the prose.
- Rule front matter: `id`, `title`, `status`, `source` (`path:line`), `domain`. Playbook front matter: `id`, `title`, `status`, `validates` (list, at least one rule id), `environment`, `targets` (list).
- An execution stores a reference and a short summary, never a payload. `summary` 1 to 500 characters; `evidence_ref` 1 to 300 characters and one of `path:line[-line]` (forward slashes, no drive letter), `http(s)://...` or a ticket id like `ABC-123`. Control characters are removed.
- Sensitive-data guard on `summary` and `evidence_ref`: refuse `ghp_`, `github_pat_`, `-----BEGIN`, an 11-digit or CPF-shaped number, a 44-digit number. The error names the rule that fired and never echoes the value.
- `trace_id` comes from `core.tracing.current_call` (`state.trace_id`, `state.caller`, `state.task_label`); outside a call it is `NULL` and `recorded_by` is `"cli"`.
- SQLite file `.runtime/evidence.db`, WAL, 5 s busy timeout; the path is resolved at call time (`path or EVIDENCE_DB`).
- `PyYAML>=6.0` in `requirements.txt`. New vault notes are written with CRLF line endings.
- Python and tests run from the repository root: `.\.venv\Scripts\python.exe -m unittest <module>` with `PYTHONIOENCODING=utf-8`. Commits: Conventional Commits, one concern each.

## Review Focus

- A `summary` or `evidence_ref` with control characters or a very long string → cleaned or refused, never stored raw.
- An `active` playbook that validates a `retired` rule → reported by lint.
- Two processes recording at the same moment → both rows stored, no `database is locked` error returned to the caller.
- A rule whose playbooks have no executions → output says "sem evidência ainda", never a pass.
- A missing or corrupt `evidence.db` → the MCP tool returns `{"error": ...}`; the server does not crash.

### Task 3: Validation, queries, lint and seed import (in `core/evidence.py`)

**Files:**
- Modify: `core/evidence.py`
- Test: `tests/test_evidence.py` (new classes)

**Interfaces:**
- Consumes: `Definitions`, `EvidenceStore` from Tasks 1 and 2.
- Produces:
  - `validate_execution(defs: Definitions, playbook_id: str, result: str, summary: str, evidence_ref: str, environment: str) -> tuple[Optional[dict], Optional[str]]` returning `(clean_fields, None)` or `(None, error_message)`; `clean_fields` has `summary` and `evidence_ref` with control characters removed.
  - `rule_evidence(defs, store, rule_id: str, limit: int = 5) -> dict`: `{"error": "...known ids..."}` or `{"rule": {...}, "playbooks": [{"id", "title", "status", "environment", "executions": [...], "note": "sem evidência ainda" when empty}]}`; `limit` clamped to 1..20.
  - `list_rules(defs, store) -> list[dict]` (id, title, status, playbooks, `latest` = date and result of the newest execution across its playbooks, or `None`).
  - `lint(defs, store: Optional[EvidenceStore] = None) -> list[str]`.
  - `import_seed(store: EvidenceStore, seed_path: Path) -> tuple[int, int]` returning `(added, skipped)`; each seed row is a dict with `import_key`, `playbook_id`, `ts`, `result`, `environment`, `evidence_ref`, `summary`; recorded with `source="imported"`, `recorded_by="cli"`.

- [ ] **Step 1: Write the failing tests** (class `TestValidate`, `TestQueries`, `TestLint`, `TestImportSeed`):
  - validate: happy path; unknown playbook; `retired` playbook; bad `result`; bad `environment` (and `local` always allowed); empty and 501-character summary; reference not matching the allowed shapes; control characters removed; each sensitive-data rule (token, CPF-shaped `123.456.789-09`, 44-digit string) → error names the rule and does not contain the value.
  - queries: `rule_evidence` with and without executions (`note == "sem evidência ainda"`), unknown rule lists known ids, `limit=999` returns at most 20; `list_rules` shape.
  - lint: one test per problem class (invalid id, duplicate, unknown rule in `validates`, `active` rule with no `active` playbook, `active` playbook validating a `retired` rule, execution for an unknown playbook when a store is given) and a clean case returns `[]`.
